# Architecture

Living document. Update this whenever a structural decision changes (new module,
new data flow, new storage layer, etc.) — keep it in sync with the actual code.

## Overview

MoneyMatter is a **Wails v2** desktop app: a Go backend renders a **React + TypeScript**
frontend inside a native webview. Single binary, no separate server process.

```
main.go / app.go (Go)  <-- Wails bridge (wailsjs) -->  frontend/src (React)
```

## Tech Stack

- **Backend**: Go 1.25, Wails v2. `modernc.org/sqlite` (via `database/sql`) and
  `github.com/google/uuid` are direct go.mod dependencies, fully wired into
  `app.go`/`internal/profile`/`internal/income` — see Backend below.
- **Frontend**: React 19 + TypeScript, Vite 7, Tailwind CSS 4 (via `@tailwindcss/vite` plugin), `recharts` (Income Overview's charts).
- **Icons**: `lucide-react` exclusively, as `<Icon size={n} className="..." />` components colored via `currentColor` (Tailwind text-color classes on the icon or a wrapping element). Material Symbols Outlined (Google Fonts) was removed entirely — no `material-symbols-outlined` class or font link remains. Use existing icon component names from `Header.tsx`/`Sidebar.tsx` for consistency (e.g. `LifeBuoy` for "Support" everywhere) rather than picking new near-duplicates per component.
- **Bridge**: `frontend/wailsjs/` — auto-generated bindings (`go/main/App.*`, `runtime/*`) that expose Go methods to the frontend and vice versa. Regenerated by `wails build`/`wails dev`, don't hand-edit.

## Frontend State & Data Flow

- `App.tsx` is the single source of truth for top-level UI state — `currentTab`
  (persisted to `localStorage` under `moneymatter.currentTab`, so a refresh
  reopens the same tab), `rawProfiles`/`currentProfileId`, `themeMode` +
  live-tracked `systemTheme`, `accent`, `baseCurrency`,
  `settingsOpen`/`supportOpen`/`chatOpen`, and `sidebarCollapsed` — and passes
  it down as props to `Header`, `Sidebar`, `IncomePage`, and the modals/popups.
- No global state library (no Redux/Zustand/Context) — plain `useState` + prop
  drilling. Revisit if state sharing gets deeper than App/Header/Sidebar/pages.
- **Mock mode**: `src/utils/mock.ts`'s `isMockMode()` checks for `?mock=true`
  in the URL. When set, `App.tsx` and the Income pages read/write
  `src/mocks/{profiles,income}.ts` instead of calling any `wailsjs` binding —
  lets the UI run in a plain browser (`npm run dev`, no `wails dev`/Go backend
  needed) for frontend-only work. Every backend-calling handler in `App.tsx`
  branches on `isMockMode()` first.
- **Theme**: `themeMode: 'system' | 'light' | 'dark'` (default `'system'`) is
  the persisted setting; `systemTheme` tracks the OS `prefers-color-scheme`
  live via a `matchMedia` change listener (seeded once from
  `getSystemTheme()`, exported by `Header.tsx`). The actual rendered
  `theme` is derived: `themeMode === 'system' ? systemTheme : themeMode`.
  Both the Header's quick dark/light toggle and the Settings popup's Default
  Theme control set `themeMode` directly. See `docs/DECISIONS.md` for the
  placement/icon decisions.
- **Profiles are backend-backed and fully CRUD**: `App.tsx` calls the
  generated `frontend/wailsjs/go/main/App` bindings (`ListProfiles`/
  `CreateProfile`/`RenameProfile`/`UpdateProfile`/`DeleteProfile`/
  `ExportProfileData`) directly — no mock profile data remains outside mock
  mode. It keeps the full `profile.Profile` list from the backend in
  `rawProfiles` state (needed because `UpdateProfile` overwrites every
  settable column at once) and derives the UI-facing `{id, name, avatar,
  color}` `Profile` shape (defined in `ProfileModal.tsx`) from it per render.
  Base Currency/Default Theme/Theme Color are persisted onto the active
  profile's row (`currency`/`base_theme`/`theme_color` columns) rather than
  living only in memory — switching profiles adopts its stored settings
  (`persistProfilePatch` fires `UpdateProfile` in the background on change),
  and deleting the current profile falls back to whichever remaining profile
  is admin. See `docs/DECISIONS.md`.
- Styling: Tailwind utility classes computed conditionally per `theme === 'dark'`
  checks (no `dark:` variant strategy configured) + CSS variables in `theme.css`
  (`:root` = dark palette, `.theme-light` = light palette overrides).

## Backend

- `App` struct in `app.go` holds `ctx`, the resolved data directory, and a
  `*profile.Store`; exposes bound methods — `Greet` (template leftover),
  profile CRUD (`ListProfiles`/`CreateProfile`/`UpdateProfile`/
  `RenameProfile`/`DeleteProfile`/`ExportProfileData`), and the income methods
  listed below — re-exposed to the frontend via `wailsjs/go/main/App.*`
  (regenerated by `wails build`/`wails dev`, or `wails generate module` to
  refresh just the TS bindings/models without a full build — useful after
  changing a bound method's signature or a package name). Consumed directly
  by `App.tsx` (see Frontend State & Data Flow above).
- **Persistence layer**, split into three packages under `internal/`:
  - `internal/paths` (package `paths`) holds only the generic, profile-agnostic
    data-dir resolution: `paths.DataDir()` resolves/creates the root data
    folder next to the running executable (`<exe dir>/MoneyMatter_Database`),
    so the app is portable — data travels with the binary rather than
    scattering into a per-user OS config location. `paths.DataDirName`
    constant controls the folder name.
  - `internal/profile` (package `profile`) owns everything profile-specific:
    the `Profile` struct, the SQLite-backed `Store` (`store.go`), the
    profile-folder helpers (`dirs.go`: `sanitizeDirName`, `EnsureProfileDirs`),
    and the zip export (`export.go`). Uses `modernc.org/sqlite` (direct
    dependency) via `database/sql`. Ids are generated with
    `github.com/google/uuid` (also direct).
  - `profile.Open(dataDir)` opens/creates the master `profiles.db` inside
    the root passed in from `paths.DataDir()`, migrates the `profiles`
    table, and seeds a fixed `guest` profile (`profile.GuestProfileID`,
    `IsAdmin: true`) on first run so the app always has a usable admin
    profile.
  - `profiles` table columns (in this order): `id` (TEXT PK, not null),
    `name` (TEXT, not null, UNIQUE), `color`, `currency`, `base_theme`,
    `theme_color` (all nullable TEXT), `is_admin` (nullable INTEGER,
    default 0), `notifications` (nullable TEXT, JSON-encoded string array —
    SQLite has no native array type). `Create`/`Update` run inside a
    transaction that clears every other profile's `is_admin` whenever the
    written profile has `IsAdmin = true`, so at most one profile is ever
    admin. `Create` always ignores any `id` on the input and generates a
    fresh UUID.
  - `profile.EnsureProfileDirs(dataDir, name)` creates, per profile (keyed by
    the profile's unique **name**, sanitized for filesystem-illegal
    characters — not its id):
    `<dataDir>/profiles/<name>/{db,income,expense,investment,taxes}` — `db`
    holds that profile's own future SQLite databases for areas that don't
    keep their database alongside their upload folder (expense/investment/
    taxes, not yet built); `income`, `expense`, `investment`, `taxes` each
    hold that area's uploaded source documents — `income` additionally holds
    `income.db` itself (see `internal/income` below, which moved its database
    there from `db/` so it travels with the docs on a profile rename).
    `profiles.<id>` (not the name) is the id every per-profile database uses
    as a foreign key back to the master `profiles` table.
  - `profile.Store.RenameProfile(id, newName)` is the only way to
    change a profile's name — it updates the DB row and `os.Rename`s the
    profile's directory together; `Update` deliberately excludes `name` from
    its `SET` clause so it can never desync the directory from the DB.
  - `profile.Store.Delete(id)` removes a profile's row and its on-disk
    directory. Refuses to delete the seeded guest profile
    (`ErrCannotDeleteGuestProfile`) or the last remaining profile
    (`ErrCannotDeleteLastProfile`) — the app always needs at least one usable
    (guest) profile. If the deleted profile was admin, the guest profile is
    promoted to admin so exactly one profile stays admin.
  - `App.shutdown` (wired via `OnShutdown` in `main.go`) closes the store's
    `*sql.DB` on app exit.
  - The zip export type is named `ProfileExport` rather than the shorter
    `Export` because Wails' binding generator treats `Export` as a reserved
    keyword and refuses to generate a frontend type for it.
  - Covered by `internal/profile/store_test.go` (admin exclusivity, name
    uniqueness, server-generated ids, rename-moves-directory, update leaves
    name untouched) and `internal/profile/export_test.go` (zip contents,
    unknown-id error).

- **Per-profile data**, `internal/income` (package `income`): the first
  database that lives inside a profile's own folder rather than the master
  `profiles.db` — `<dataDir>/profiles/<name>/income/income.db` (alongside the
  per-stream document directories, so it moves as one unit with a profile
  rename). `App.migrateLegacyIncomeDB` moves an `income.db` found at its old
  location (`<profile>/db/income.db`, from before it was relocated into
  `<profile>/income/`) into place on first open after an upgrade — a no-op
  for every profile created after the move. `App` opens and closes this
  database per call (`openIncomeStore` in `app.go`) rather than holding a
  long-lived handle like it does for the master `profile.Store`, since a
  handle held open across a `RenameProfile` call could collide with that
  call's `os.Rename` of the same directory on Windows.
  - `income_streams` table: `id` (TEXT PK), `profile_id` (FK back to
    `profiles.id`), `name` (UNIQUE NOT NULL — also what the stream's
    document folder is named after, see below), `source_type` (`both` |
    `account` | `cash`), `tax_status` (`both` | `taxed` | `non_taxed`),
    `bank_account` (required when `source_type` is `account` or `both`,
    enforced in Go), `last_updated`. `income.Store.UpdateStream` excludes
    `name` from its `SET` clause, mirroring `profile.Store.Update` excluding
    `name` — a stream can't be silently renamed out of sync with its
    on-disk folder.
  - `income_entries` table (renamed from `payslips` — the Go `Payslip`
    struct is now `Entry`, since a row here can be a payslip or any other
    proof-of-income document): `id` (TEXT PK), `name` (UNIQUE NOT NULL),
    `income_stream_id` (FK → `income_streams.id`), `month_year` (`MM/YY`,
    required) + `day` (`DD`, optional), validated by regex in Go, not
    enforced by SQLite, `source_type`/`tax_status` restricted to
    `account`/`cash` and `taxed`/`non_taxed` (no `both` on a single entry),
    `bank_account` (required when `source_type` is `account`), `amount`
    (required, must be > 0) / `tax_amount` / `deductions`, `directories`
    (JSON-encoded string array of uploaded document paths), `last_updated`.
    A profile's `income.db` created before this rename still has a
    `payslips` table on disk — `Store.migrate` renames it to
    `income_entries` on open (`renameLegacyPayslipsTable`), same
    detect-and-migrate pattern as the earlier legacy `date` column drop.
  - `income.EnsureStreamDir(profileIncomeDir, streamName)` (in
    `internal/income/dirs.go`) creates
    `<dataDir>/profiles/<name>/income/<sanitized stream name>/` — called
    from `App.CreateIncomeStream` right after the DB insert — as the
    directory a stream's uploaded income-entry files live under (the paths
    an `Entry.Directories` entry would point at).
  - `paths.SanitizeDirName(name, fallback)` (moved out of
    `internal/profile/dirs.go`, which now just wraps it) is shared by both
    `profile` and `income` so a profile directory and an income-stream
    directory sanitize identically.
  - `profile.Store` gained `DBDir(id)` and `IncomeDocsDir(id)` so `income`
    (and future per-profile-database packages) can locate a profile's `db/`
    and `income/` folders without reaching into `profile`'s private
    `profileDir` helper.
  - Bound on `App`: `ListIncomeStreams`/`CreateIncomeStream`/
    `UpdateIncomeStream`/`DeleteIncomeStream` (keyed by `profileId`), and
    `ListIncomeEntries`/`CreateIncomeEntry`/`UpdateIncomeEntry`/
    `DeleteIncomeEntry` (take an explicit `profileID` argument, since
    `income_entries` itself carries no profile id column — it's only used
    to pick which profile's `income.db` to open). `DeleteIncomeStream`
    removes the stream, every entry recorded against it, their attachment
    files, and the stream's document directory — file/directory removal is
    best-effort (logged, not fatal) since the database rows are the source
    of truth. `App.SaveIncomeAttachment`/`ReadIncomeAttachment`/
    `DeleteIncomeAttachment` write/read/remove the raw files referenced by an
    `Entry.Directories` path (under `<profile>/income/<stream name>/`) — the
    frontend is responsible for giving `SaveIncomeAttachment` a unique file
    name (e.g. prefixed with the entry id) so two attachments don't collide.
    Fully wired into `IncomePage.tsx`/`IncomeOverview.tsx`.
  - Covered by `internal/income/store_test.go`.

## Planned Direction (from docs/INSTRUCTIONS.md)

Import/export of financial records (JSON/XML), document management (payslips,
statements, tax forms), investment tracking, and expense analytics/charts are
the target feature set. **Profiles and Income are fully implemented**
end-to-end (SQLite-backed CRUD, per-profile document storage, attachment
upload/download, wired into `App.tsx`/`IncomePage.tsx`/`IncomeOverview.tsx`).
Expense, Investment, Taxes, Mapper, and Vault remain UI shell only (Sidebar
nav entries exist; their pages aren't built) or are backed by placeholder
handlers (`console.log`) still on `App.tsx` (search, add-transaction, alerts).
